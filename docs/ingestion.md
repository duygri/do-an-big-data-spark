# NYC Taxi ingestion and Bronze layer

The pipeline source is exactly six NYC yellow taxi monthly CSV files, January through June 2020. Keep them under `data/raw/nyc_taxi/`, along with `taxi+_zone_lookup.csv` and `taxi_zones/`. Any local 2019 files remain on disk but are excluded by the default glob `yellow_tripdata_2020-0[1-6].csv`. Neither source files nor generated Parquet belong in Git.

Copy `configs/config.example.yaml` to `configs/config.yaml`, then run `python -m src.pipeline.main --config configs/config.yaml` from the repository root. The NYC taxi pipeline validates the matched filenames before Spark starts: all six months must be present, and any month outside this range causes a clear error. The generic `read_raw` helper still supports CSV and JSON; the end-to-end cleaning pipeline requires the yellow taxi CSV schema. Input path, header, reader options, Bronze path, Spark master, and maximum file partition size are configurable. Paths are relative to the current working directory.

The CSV schema has 18 nullable fields in source order. `VendorID`, `passenger_count`, `RatecodeID`, `PULocationID`, `DOLocationID`, and `payment_type` are integers. Pickup and dropoff datetime are timestamps using `yyyy-MM-dd HH:mm:ss`. `store_and_fwd_flag` is a string. Trip distance and all fare, tax, tip, toll, surcharge, and total amounts are doubles. Blank numeric cells, including early `congestion_surcharge` values, become null. CSV parsing uses FAILFAST for malformed nonblank values; validation and cleaning remain separate team stages. The zone lookup and shapefile are retained as raw reference data but are not loaded by this stage.

The pipeline writes Snappy Parquet to `data/bronze/raw/`, reads it back, and compares its schema and row count with the input. It then cleans Bronze into `data/silver/cleaned/` and writes a quality report. It stops Spark on success or failure. See [cleaning and quality policy](cleaning-quality.md). `data/gold/` remains reserved for downstream transformation.
